## 第二部分：我已有答案，請老師確認方向

2. **主軸放「預測＋預警」，還是「通勤流動分析」？**
   → **預測＋預警為主**，流動分析（哪裡借、哪裡還、尖峰時段）放在 EDA。預警比較像產品，展示效果好。

3. **範圍要做全臺北 1,800 站，還是先聚焦一區？**
   → **全臺北用同一個模型**，開發時先用一區（例如大安區）把流程跑通。快照只能收約 4 週，全臺北的資料量多 8 倍，對模型很重要。

4. **即時資料只能自己收約 4 週，夠訓練模型嗎？**
   → 用**兩段式**降低風險：
   - 第一段：12 個月歷史資料 → 預測每站每小時借出／還入量（資料充足）
   - 第二段：自己收的快照＋第一段的結果 → 預測 30 分鐘後空站／滿站
   - 就算第二段資料不夠，第一段也能獨立交出成果。

5. **歷史資料要用幾年？**
   → **最近 12 個月（2025/08 – 2026/07）**，涵蓋四季與寒暑假；照時間切成訓練（前 10 個月）、驗證（6 月）、測試（7 月）。

7. **要不要加新北市資料？**
   → **預測不涵蓋新北**；做流動分析時，把新北的站統一歸成「新北」一類，保留跨市移動的資訊但不擴大範圍。

8. **成果呈現：Streamlit 儀表板＋LINE Bot，還是只做一個？**
   → **儀表板為主**（公開網址、地圖顯示各站風險、資料延遲時有警示），**LINE 定時推播為加分**，時間夠才做。

9. **模型評估用什麼指標？**
   → **PR-AUC**，以及「精準度 0.5 時的 Recall」（白話：推播兩次至少一次是對的，能抓到多少真的缺車）。
   - 和兩個 baseline 比：「維持現狀」（現在少車就猜會缺）、「上週同時段」。
   - 另外單獨報告**轉變案例**（現在還有車、30 分鐘後沒車），這才是預測真正有價值的地方。

## 第三部分：目前進度（截至 11/03）

### 已完成：自動收集管線

```
YouBike 即時 API
      │ 每 10 分鐘
      ▼
收集器（GitHub Actions ＋ 本機備援）
      │ 精簡 6 個欄位、gzip 壓縮
      ▼
GitHub data 分支：snapshots/raw/日期/時間.csv.gz
      │ 每天 00:35
      ▼
每日整併 → snapshots/日期.parquet ＋ quality/daily.csv（遺漏率報表）
```

- 程式：Python＋Polars，24 個自動化測試，push 時自動執行。
- 公開 repo：https://github.com/yantingque/youbike-radar

### 遇到的問題與處理

- **GitHub Actions 的排程不準**：設定每 10 分鐘，實際上新 repo 一天只觸發幾次，每日整併也延遲了 7 小時才跑。
  → 加上**本機電腦每 10 分鐘收集**當備援，兩邊都推到同一個分支，重複的資料在整併時會自動去除。
- **電腦自動更新重開機**：11/03 早上中斷約 6 小時。
  → 改設 Windows 更新的使用時段，避免半夜重開機；遺漏率報表會如實記錄缺口。
