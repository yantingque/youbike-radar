> **v0.2 修改說明（與 Adam 老師討論後）**
> 1. **資料分工**：歷史租借資料用來**訓練**模型；即時資料用來當**預測輸入**（現在車數）和**答案**（一小時後的真實車數）。

> 5. **開發環境與時程**：改在 Google Colab 撰寫，每週照課程範本（W1 了解與檢查 → W2 處理 → W3 分析 → W4 演算法）推進。

## 1. 我的專案主題

**用臺北市 YouBike2.0 的即時與歷史開放資料，分析各站借還車的時空規律，並預測「哪個站、什麼時候會借不到車或還不了車」，再用 LINE Bot 提前通知使用者。**

> 主題變更說明：原企劃書的方向是房價／股價分析。改為 YouBike 的原因：
> 1. 股價預測已經有兩個作品（stock-system、stock-ml-tracker），再做一個同類型的作品，作品集的廣度不夠。
> 2. YouBike 資料有「即時＋歷史」、「時間＋空間」兩個面向，能展示更多種技能（資料工程、地理視覺化、時間序列）。
> 3. 每個人都騎過 YouBike，面試時很容易講清楚問題和價值。

## 2. 我的專案目標

### 2-1 製作專案的原因

- **使用者痛點**：通勤尖峰時間，捷運站旁的 YouBike 站常常「到了才發現沒車」或「要還車卻沒位子」，只能繞去下一站。
- **資料面**：臺北市每天約 25 萬趟租借（2026/07 實測 759 萬筆／月），而且即時資料每分鐘更新、歷史資料從 2020 年起都公開，資料量夠大、夠真實。
- **個人面**：12 月開始求職，需要一個從資料蒐集、清理、分析、建模到上線服務的完整代表作。

### 2-2 想達成的專案成果

| 成果 | 說明 | 驗收標準 |
|---|---|---|
| ① 即時快照累積 | 每 10 分鐘抓一次全臺北站點車數，當作驗證預測的答案（已上線） | 連續運作 ≥ 4 週，遺漏率 < 5% |
| ② 探索性分析報告 | 尖峰時段、熱門站點、通勤潮汐、OD 流動、天氣影響 | 至少 8 張有結論的圖表 |
| ③ 需求預測模型＋缺車預警 | 用歷史資料預測各站下一小時淨流量，加上現在車數估計一小時後車數，≤ 2 台就預警 | 淨流量誤差贏過 baseline（上週同時段）；用即時快照算預警命中率、漏報率 |
| ④ 互動儀表板 | 地圖顯示各站即時狀態＋預測風險 | 可公開網址瀏覽 |
| ⑤ LINE Bot 預警（加分） | 使用者設定常用站，快空站時推播提醒 | 能實際收到推播 |
| ⑥ GitHub 專案＋成果簡報 | README、架構圖、分析結論 | 可直接放進履歷 |

### 3-2 已確認的資料限制（會影響專案設計）

1. **即時資料沒有歷史** → 必須自己收集。收集程式從 11/02 起每 10 分鐘運作，累積的快照用來**對答案**（驗證一小時後的真實車數）。
2. **歷史租借紀錄只到整點、只有站名沒有站點代號** → 分析單位定為「站 × 小時」，預測也以「下一小時」為單位；用站名對照（實測 99.5% 可直接對上）。
3. **借還相減 ≠ 站上車數**（因為有人工調度） → 模型只預測「淨流量」（歷史資料），「站上車數」一律以即時資料為準。
4. **歷史資料最新到 2026/07，和 11 月的即時資料沒有重疊** → 剛好分工：歷史資料訓練，即時資料驗證。
5. 單月檔案近 1 GB → 整份統計用 DuckDB 直接查 CSV，逐列檢查才抽樣讀進 pandas（Colab 免費版記憶體約 12 GB）。

### 4-3 分析與建模設計

**分析問題（EDA）**
1. 一天中哪些時段最多人借？平日 vs 假日差在哪？
2. 哪些站是「早上被借光、晚上被還滿」的通勤潮汐站？
3. 最熱門的起訖路線是哪些？是不是集中在捷運站接駁？
4. 下雨、氣溫、假日對使用量影響多大？
5. 電輔車和一般車的騎乘距離／時間有沒有差？

**預測任務（兩步：先預測，再套規則預警）**

1. **需求預測模型**（迴歸，用歷史資料訓練）
   - **目標**：站點 *s* 在下一小時的**淨流量 = 還入量 − 借出量**（正數代表車變多，負數代表車變少）
   - **特徵**：時段、星期、是否假日；該站過去同時段的淨流量（上週、近 4 週平均）；天氣（降雨、氣溫）；站點屬性（容量、行政區、是否在捷運站旁）
   - **Baseline**：上週同一時段的淨流量
   - **評估**：MAE、RMSE（依時間切分：前 10 個月訓練、6 月驗證、7 月測試）
2. **缺車預警規則**（不另外訓練模型）
   - `估計一小時後車數 = 即時 API 的現在可借車數 + 預測淨流量`
   - 估計值 ≤ 2 台 → 預警「快借不到車」；`容量 − 估計值 ≤ 2` → 預警「快還不了車」
   - **對答案**：用每 10 分鐘收集的快照取一小時後的真實車數，計算預警的**命中率**（預警的站真的缺車的比例）與**漏報率**（真的缺車卻沒預警的比例）

> 為什麼不用「風險模型」（直接訓練空站分類器）：分類器要用站上車數訓練，但站上車數只有自己收集的幾週快照，資料太少。先預測淨流量再套規則，歷史資料就夠用，也比較好解釋。時間夠的話，分類器列為加分項。

### 4-4 系統架構

```
【訓練】
 歷史租借 zip（每月）──→ DuckDB 彙總成「站 × 小時」
                          借出量、還入量、淨流量
                                 │ ＋ 天氣、假日
                                 ▼
                         需求預測模型（下一小時淨流量）
                         和 baseline 比：上週同時段

【預測 → 預警 → 對答案】
 即時 API：現在可借車數 ─┐
 模型：下一小時淨流量 ───┴─→ 估計一小時後車數 ──→ ≤ 2 台 → 儀表板標紅／LINE 推播
                                     │
                                     ▼
 每 10 分收集的快照：一小時後的真實車數 ──→ 對答案（預警命中率、漏報率）
```

### 4-6 風險與因應

| 風險 | 影響 | 因應 |
|---|---|---|
| 自己收集的即時資料只有約 4 週 | 不夠拿來訓練 | 不用快照訓練，只用來對答案；訓練全部用歷史資料 |
| 歷史資料沒有站上車數、有人工調度 | 估計的車數會和實際有落差 | 預警規則每次都從即時 API 的現在車數起算，只往後估一小時，誤差不會累積；落差在對答案時如實報告 |
| 歷史檔案太大、Colab 記憶體有限 | 跑不動 | DuckDB 直接查 CSV／先轉 Parquet；W1 只用 1 個月，W2 起再擴大到 12 個月 |
| 時程太緊 | 做不完 | LINE Bot、調度建議列為加分項，主線只到儀表板 |
| GitHub Actions cron 不準時（常延遲數分鐘） | 收集間隔不均 | 存 `collect_time`，分析時對齊到 10 分鐘格點；必要時改本機排程 |
