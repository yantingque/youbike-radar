## 1. 我的專案主題

**用臺北市 YouBike2.0 的即時與歷史開放資料，分析各站借還車的時空規律，並預測「哪個站、什麼時候會借不到車或還不了車」，再用 LINE Bot 提前通知使用者。**

> 主題變更說明：原企劃書的方向是房價／股價分析。改為 YouBike 的原因：
> 1. 股價預測已經有兩個作品（stock-system、stock-ml-tracker），再做一個同類型的作品，作品集的廣度不夠。
> 2. YouBike 資料有「即時＋歷史」、「時間＋空間」兩個面向，能展示更多種技能（資料工程、地理視覺化、時間序列）。
> 3. 每個人都騎過 YouBike，面試時很容易講清楚問題和價值。

## 2. 我的專案目標

### 2-1 製作專案的原因

- **使用者痛點**：通勤尖峰時間，捷運站旁的 YouBike 站常常「到了才發現沒車」或「要還車卻沒位子」，只能繞去下一站。
- **資料面**：臺北市每天約 25 萬趟租借（2026/07 實測 759 萬筆／月），而且即時資料每分鐘更新、歷史資料從 2020 年起都公開，資料量夠大、夠真實。
- **個人面**：12 月開始求職，需要一個從資料蒐集、清理、分析、建模到上線服務的完整代表作。

### 2-2 想達成的專案成果

| 成果 | 說明 | 驗收標準 |
|---|---|---|
| ① 自動資料收集管線 | 每 10 分鐘抓一次全臺北站點車數，存成歷史資料 | 連續運作 ≥ 4 週，遺漏率 < 5% |
| ② 探索性分析報告 | 尖峰時段、熱門站點、通勤潮汐、OD 流動、天氣影響 | 至少 8 張有結論的圖表 |
| ③ 缺車／滿站預測模型 | 預測各站未來 30 / 60 分鐘是否會「空站」或「滿站」 | 贏過 baseline（「上週同一時間」） |
| ④ 互動儀表板 | 地圖顯示各站即時狀態＋預測風險 | 可公開網址瀏覽 |
| ⑤ LINE Bot 預警（加分） | 使用者設定常用站，快空站時推播提醒 | 能實際收到推播 |
| ⑥ GitHub 專案＋成果簡報 | README、架構圖、分析結論 | 可直接放進履歷 |

## 3. 資料搜集

### 3-1 資料來源（詳見 [01 資料來源與資料定義](01_資料來源與資料定義.md)）

| 類型 | 資料 | 規模（實測） |
|---|---|---|
| 即時 | 臺北市 YouBike2.0 即時站點 JSON（免金鑰，每分鐘更新） | 1,823 站、51,781 車柱 |
| 歷史 | YouBike2.0 票證刷卡資料（每月 zip） | 2020/04 ~ 2026/07 共 76 個月；單月 759 萬筆、約 890 MB |
| 外部 | 中央氣象署逐時天氣、政府行政機關辦公日曆 | — |
| 參考 | UCI Bike Sharing（華府）、UCI Seoul Bike Sharing、Kaggle notebooks | — |

### 3-2 已確認的資料限制（會影響專案設計）

1. **即時資料沒有歷史** → 必須自己收集。收集腳本已完成（`scripts/collect_realtime.py`），**諮詢後立刻開始排程**，越早開始，訓練資料越多。
2. **歷史租借紀錄只到整點、只有站名沒有站點代號** → 分析單位定為「站 × 小時」；用站名對照（實測 99.5% 可直接對上）。
3. **借還相減 ≠ 站上車數**（因為有人工調度） → 「需求量」用歷史資料分析，「站上車數」用自己收集的即時資料。
4. 單月檔案近 1 GB → 改用 DuckDB 或 Polars，不用 pandas 一次讀完。

## 4. 專案執行規劃

### 4-1 專案名稱定錨

📝 **專案名稱（暫定）**：**「YouBike 有車嗎？— 臺北 YouBike 站點供需預測與缺車預警系統」**

備選：
- 「臺北 YouBike 通勤潮汐分析與站點缺車預測」（偏分析）
- 「BikeRadar：YouBike 即時缺車預警 LINE Bot」（偏產品）

### 4-2 專案使用技術

| 層 | 技術 | 用途 |
|---|---|---|
| 資料收集 | Python `requests`、GitHub Actions（cron）或 Windows 工作排程器 | 每 10 分鐘抓即時資料 |
| 資料儲存 | CSV / Parquet、DuckDB | 處理 GB 級歷史資料 |
| 資料清理 | Polars / pandas | 站名對照、異常值（騎乘 > 4 小時）、缺漏日檢查 |
| 分析視覺化 | Plotly、Folium / Kepler.gl | 時間熱力圖、站點地圖、OD 流向圖 |
| 建模 | scikit-learn、LightGBM / XGBoost | 空站／滿站分類、需求量迴歸 |
| 評估 | 時間序列交叉驗證、baseline 比較 | 避免用未來資料預測過去 |
| 呈現 | Streamlit 儀表板 | 地圖＋預測風險 |
| 推播（加分） | LINE Messaging API | 常用站快空時提醒 |
| AI 協作 | Claude Code ＋ superpowers ＋ mattpocock/skills | 需求釐清、規格、任務拆解、TDD |

### 4-3 分析與建模設計

**分析問題（EDA）**
1. 一天中哪些時段最多人借？平日 vs 假日差在哪？
2. 哪些站是「早上被借光、晚上被還滿」的通勤潮汐站？
3. 最熱門的起訖路線是哪些？是不是集中在捷運站接駁？
4. 下雨、氣溫、假日對使用量影響多大？
5. 電輔車和一般車的騎乘距離／時間有沒有差？

**預測任務**
- **目標**：站點 *s* 在時間 *t* 之後 30 / 60 分鐘，「可借車 = 0」或「可還位 = 0」的機率
- **特徵**：
  - 目前車數、過去 1 小時車數變化
  - 時段、星期、是否假日
  - 該站歷史同時段平均淨流量（來自歷史租借紀錄）
  - 天氣（降雨、氣溫）
  - 站點屬性（容量、行政區、是否在捷運站旁）
- **Baseline**：上週同一時間的狀態
- **評估**：Precision / Recall（漏報「會空站」的代價較高，著重 Recall）、PR-AUC

### 4-6 風險與因應

| 風險 | 影響 | 因應 |
|---|---|---|
| 自己收集的即時資料只有約 4 週 | 預測模型訓練資料少 | 先用歷史租借紀錄做「需求量預測」，即時資料做「空站預警」，兩條線並行 |
| 歷史檔案太大 | 電腦跑不動 | DuckDB 直接查 CSV／先轉 Parquet；先只取近 12 個月 |
| 時程太緊 | 做不完 | LINE Bot、調度建議列為加分項，主線只到儀表板 |
| GitHub Actions cron 不準時（常延遲數分鐘） | 收集間隔不均 | 存 `collect_time`，分析時對齊到 10 分鐘格點；必要時改本機排程 |
