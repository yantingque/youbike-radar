## 1. 目的與使用者

- **目的**：12 月求職用的代表作，完整展示「資料收集 → 清理 → 分析 → 建模 → 呈現」。
- **使用者**：通勤族。要回答的問題是：「我常去的那一站，**一小時後**還有沒有車、有沒有位子？」
- **判斷好壞的標準**：面試官看得懂、相信它真的有用，而不是準確度做到最高。

## 2. 和 v1 相比改了什麼

| 項目 | v1（11/02） | v0.2（現在） | 理由 |
|---|---|---|---|
| 資料分工 | 歷史資料和即時快照都拿來訓練 | **歷史資料訓練；即時資料只當預測輸入和答案** | 老師建議；快照只有幾週，不夠訓練 |
| 模型 | 兩段式：需求模型 → 風險模型（分類器） | **需求預測模型＋預警規則**，不訓練分類器 | 老師問「不是直接預測後推播嗎？」；規則比較好解釋 |
| 預測時間 | 30 分鐘後 | **下一小時** | 歷史資料只精確到整點 |
| 收集器的角色 | 訓練資料來源 | **驗證答案的來源**（一小時後的真實車數） | 跟著資料分工改 |
| 開發環境 | 本機、TDD、Actions 預測器 | **Google Colab，每週一本 notebook** | 使用者要邊學邊寫 |
| 時程 | 依元件排 | **依課程範本每週一段（W1 → W5）** | 配合課程 |

## 3. 已定案的決策

| 決策 | 結論 |
|---|---|
| 訓練資料 | 歷史租借紀錄，最近 12 個月（2025/08 ~ 2026/07）。W1 先只用 2026/07 |
| 分析單位 | 站 × 小時 |
| 預測目標 | 下一小時的**淨流量 = 還入量 − 借出量**（迴歸） |
| 預警規則 | `估計車數 = 即時 API 的現在可借車數 + 預測淨流量`；估計車數 ≤ 2 → 「快借不到車」；`容量 − 估計車數 ≤ 2` → 「快還不了車」 |
| 對答案 | 用收集器的快照取一小時後的真實車數，算預警的命中率與漏報率 |
| 範圍 | 全臺北一個模型；新北市不預測 |
| 成果形式 | Streamlit 儀表板為主；LINE 推播為加分 |
| 大檔處理 | 整份統計用 DuckDB 直接查 CSV；逐列檢查才抽樣讀進 pandas（Colab 記憶體約 12 GB） |
| 存放位置 | zip 存 Google Drive（`MyDrive/youbike/raw`）；CSV 解壓縮到 Colab 本機 `/content` |

## 4. 系統流程

```
【訓練】
 歷史租借 zip（每月）──→ DuckDB 彙總成「站 × 小時」
                          借出量、還入量、淨流量
                                 │ ＋ 天氣、假日
                                 ▼
                         需求預測模型（下一小時淨流量）
                         和 baseline 比：上週同時段

【預測 → 預警 → 對答案】
 即時 API：現在可借車數 ─┐
 模型：下一小時淨流量 ───┴─→ 估計一小時後車數 ──→ ≤ 2 台 → 儀表板標紅／LINE 推播
                                     │
                                     ▼
 每 10 分收集的快照：一小時後的真實車數 ──→ 對答案（預警命中率、漏報率）
```

收集器（`ubike/`、GitHub Actions＋本機備援）照常運作，程式不改。

## 5. 模型與評估

### 5-1 需求預測模型

- **特徵**：小時、星期、假日／補班、逐時雨量與氣溫、站點容量、行政區、離最近捷運站距離、該站上週同時段的淨流量、近 4 週同時段平均
- **切分**：照時間，2025/08 ~ 2026/05 訓練、2026/06 驗證、2026/07 測試，不隨機切
- **Baseline**：上週同時段的淨流量
- **指標**：MAE、RMSE；另外報告尖峰時段（07–09、17–19）

### 5-2 預警規則

- **Baseline**：維持現狀（假設一小時後車數等於現在）
- **指標**：命中率（發出預警的站，真的缺車的比例）、漏報率（真的缺車，卻沒有預警的比例）；另外報告轉變案例（現在 > 2 台、一小時後 ≤ 2 台）

## 6. 已知的資料問題（W1 查證，2026/07 檔）

這些問題會影響 W2 的處理方式和模型設計。數字都是實際跑出來的。

| 問題 | 實測 | 對設計的影響 | W2 處理方向 |
|---|---|---|---|
| **資料缺口** | 7/10 08:00 → 7/12 06:00 完全沒有紀錄（約 47 小時），7/10 07:00 和 7/12 07:00 只有部分資料 | 7/17、7/18 的「上週同時段」特徵會缺值 | 標記為缺漏，**不能補 0**；其他月份也要用同樣方法檢查 |
| **`rent` 型態被猜錯** | DuckDB 只看前 20,480 列，判斷成 TIME；實際有超過 24 小時的值 | 讀檔時要指定 `types={'rent': 'VARCHAR'}` | 轉成「騎乘分鐘數」 |
| **騎乘時間極端值** | 中位數 8.1 分鐘；> 24 小時 382 筆，最長 386 小時；> 4 小時 6,104 筆；< 1 分鐘 13,067 筆；0 秒 7 筆 | 極端值不代表正常需求 | 決定上下限；先標記，不刪 |
| **完全相同的資料列** | 19,772 組，多出 20,613 列（0.27%），最多一組 9 次 | 沒有 ID，分不出是重複記錄還是巧合（熱門路線、秒數相同） | **保留**，不刪 |
| **疑似夜間調度** | 相鄰兩站互騎、約 1 分鐘、集中在 0–6 點（例：福星公園 ↔ 福星公園地下停車場，3 點約 350 筆／月） | 不是真正的使用需求，會灌大深夜的淨流量 | 定義規則標記，W3 分析時確認，建模時考慮排除 |
| **還車站空白** | 4 筆，其他欄位正常 | 借出量可以用，還入量少 4 筆 | 數量極少，借出量照算 |
| **`infodate`** | 跟 `rent_time` 的日期 100% 相同 | 欄位重複 | 只留 `rent_time` |
| **公開延遲** | 2026/07 的資料在 2026-09-07 才上架 | 歷史資料只能訓練，不能預測現在 | 已反映在資料分工 |
